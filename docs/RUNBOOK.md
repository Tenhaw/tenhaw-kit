## Prepare and publish exact archives

See [RELEASING.md](RELEASING.md) for the full commands and account requirements.

1. Review the change and consistent package, Python, MCP and agent-manifest versions on a branch. Run required CI, clean packed installations and the public-copy checks, then merge the reviewed candidate. A fix to an immutable published release needs a new version.
2. Dispatch `release.yml` on that exact main commit with `mode=prepare`, the reviewed version, `python_project=all` and no `source_run_id`. Prepare is the default and cannot publish. It runs shared verification and freezes 17 archives plus the bundle/source manifests in `verified-distributions-<version>-<source-sha>`.
3. Record the successful prepare run ID and freeze both source SHA and bundle. Every publishing run supplies that same `source_run_id`, version and main SHA. Reuse checks the producer workflow, source/run/artifact identity, strict inventory, download digest and every archive hash; it never rebuilds. Do not merge source changes during a partially completed publication.
4. For a genuinely new PyPI project, register one pending publisher and select `mode=python-bootstrap` with that exact `python_project`. PyPI allows only one pending registration for this shared publisher identity at a time. Complete and verify each new library before the metapackage, reusing the original prepare bundle. Existing projects use their established publishers; they do not need new pending registrations. A scoped bootstrap skips npm, satellites and the final GitHub Release.
5. Select explicit `mode=release`, `python_project=all`, the original prepare run ID and the satellite mode only after authentication and the reviewed bundle are ready. Independent npm and PyPI jobs enter the protected `release` environment and publish or verify the unchanged files. Existing public files are accepted only when their immutable integrity matches. Registry visibility and attestations may appear after an accepted upload; use the bounded verifier and inspect its actual result before repeating a run. Never create a new prepare bundle to recover a partially published version.
6. Verify exact public versions, provenance/attestations and clean public installs. In `satellite_sync=owner-cli` mode, the workflow intentionally skips the App job; the existing authenticated Tenhaw owner runs the printed sync command from a clean checkout of the exact released source. Read back all six source markers, tags, releases, template flags and topics. A green package release does not prove satellite completion. Recurring `github-app` mode requires the separately configured restricted App.
7. Verify the public CLI scaffold with the pinned Node/pnpm versions, then install and build a generated starter. Prove one real deployment from the public template source using synthetic data. Record the source tag, build result, URL and actual page checks separately from local workspace tests.
8. After the requested npm MCP version and canonical deployment are healthy, use the protected registry workflow and verify its exact public entry. Other directory submissions and launch drafts remain separate owner actions; no workflow submits forms or posts messages.

## Runtime and account boundaries

- GitHub: retain protected main, required CI/CodeQL and the protected `release` environment. The initial satellite owner mode uses the existing Tenhaw `gh` session without extracting a token or changing global Git configuration. The recurring App needs access only to the six satellites, with Contents: write, Administration: write and Metadata: read.
- npm: retain each package's trusted publisher for `Tenhaw/tenhaw-kit`, workflow `release.yml`, environment `release`, with direct publication permitted. Publishing jobs require Node >=22.14 and npm >=11.5.1. If a future new package needs authenticated ownership bootstrap, use a distinct reviewed bootstrap version/tag, then configure OIDC. Do not publish a production version without provenance and expect to replace it later.
- PyPI: the four existing projects use the configured `Tenhaw/tenhaw-kit`, `release.yml`, `release` identity. Register pending publishers only for future new projects. Preserve selected-project scope and matching-existing-file recovery; never broaden a scoped bootstrap to publish all projects.
- Vercel: retain the `tenhaw-kit-docs` and `tenhaw-mcp` project roots `apps/docs` and `apps/mcp-remote`, `lhr1` region and Standard build machine. Keep the configured service CNAME targets from [REGISTRY_IDENTITY.md](REGISTRY_IDENTITY.md); do not alter apex or nameserver records.
- Remote rate limiting: native Vercel Firewall is selected for `/mcp` and `/api/v1/*`, 30 requests per IP per 60 seconds with HTTP 429. Keep `TENHAW_RATE_LIMIT_PROVIDER=vercel` and the active rule in sync; production fails closed without the selected control. Upstash is optional and is not required by this deployment.
- MCP identity: keep `MCP_PRIVATE_KEY` only in the protected environment and `MCP_HTTP_AUTH_CONFIGURED=true` only while the exact live HTTP proof is verified. No apex TXT record is needed. The registry workflow validates proof, package version and health commit before publication.

## Verification commands

Run the required checks for the change: `pnpm check`, `uv run pytest`, `uv run ruff check`, `uv run mypy`, `uv run python scripts/sync-python-assets.py --check`, `pnpm build:apps`, `pnpm build:templates` and `pnpm pack:check`. Shared CI additionally runs all five template browser journeys and production dependency audits. Save results against their exact commit; do not infer a new test result from an unchanged historical report.

Production verification compares health to deployed main, inspects the exact remote inventory, rejects local-only tools and raw delivery events, checks the body cap and observes real rate limiting. Confirm canonical docs discovery endpoints and JSON-LD parsing/expected identity. Preserve package signatures and attestation evidence, not merely search results. [The submission pack](../launch/submissions.md) distinguishes protocol checks from unrun Claude/ChatGPT conversation reviews and portal approval.
